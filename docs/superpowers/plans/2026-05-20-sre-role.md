# Plan: Requirements Engineer (SRE) role

Status: **deferred** — captured for later, not started.
Created: 2026-05-20.

## Why

Current app has one user role: the *stakeholder* who runs the
AI-assisted interview. A real SDLC has a second role — the
**Requirements Engineer** — whose job is to *curate* the output, not
to be interviewed. Without an SRE-facing view, the spec the developer
team receives is whatever the stakeholder happened to say verbatim,
with no review, prioritization, or acceptance criteria.

## What the SRE actually does (in scope order)

1. **Reviewer** — read transcripts + auto-extracted requirements,
   mark each one approved / needs-clarification / rejected.
2. **Curator** — edit statements, change type, merge near-duplicates,
   split overly broad requirements, add priority + acceptance criteria.
3. **Cross-project owner** — see ALL stakeholders' sessions (not just
   their own), aggregate the same project across multiple stakeholders
   into one combined spec.

## Proposed page layout

Different layout from the stakeholder's 3-panel chat. SRE's primary
view is a **requirements table**, not a chat.

```
┌────────────────────────────────────────────────────────────────────┐
│  [Search…]  Project: [All v]  Type: [All v]  Status: [Pending v]   │
├────────────┬───────────────────────────────────────────────────────┤
│ Projects   │  ID    Statement                  Type   Pri   Status │
│ ▾ POS app  │  R001  Create to-do items.        FN     M     review │
│   • S1     │  R002  Sync to Google Calendar.   FN     M     review │
│   • S2     │  R003  P95 latency < 3s.          NFR    S     approv │
│ ▾ WanderS  │  R004  Strikethrough on done.     FN     C     approv │
│   • S5     │                                                       │
├────────────┴───────────────────────────────────────────────────────┤
│ Selected: R001  "Create to-do items."                              │
│ Statement: [Create to-do items.            ]   Type: [Function v]  │
│ Priority:  [Must v]      Status: [Pending Review v]                │
│ Acceptance criteria:                                                │
│   [ Given a user is signed in, When they tap +, Then …          ]  │

└────────────────────────────────────────────────────────────────────┘
```

Left rail: tree of projects → sessions (read-only browse across all
stakeholders the SRE has access to).
Center: filterable table of every requirement matching the current
filter. Click a row to load it into the bottom drawer.
Bottom: detail/edit drawer for the selected row.

## Backend changes implied

- **`role` field on `users`** — `"stakeholder" | "requirements_engineer"`.
  Default `stakeholder` on signup. Promotion happens manually
  (admin script or environment-bootstrap user).
- **New requirement fields**:
  - `priority`: `"must" | "should" | "could" | "wont"` (MoSCoW)
  - `status`: `"pending" | "approved" | "rejected" | "needs_clarification"`
  - `acceptance_criteria`: free text (Given/When/Then)
  - `edited_by` + `edited_at`: audit trail
- **PATCH endpoint** — `PATCH /requirements/{id}` for SRE edits.
  Stakeholder cannot use it.
- **Authorization shift** — the per-user `user_id` filter on
  `GET /sessions` and `GET /requirements` must be conditional:
  SRE sees all sessions across users; stakeholder still scoped to own.

## Frontend changes implied

- New route `/spec` (or `/curate`) gated by `role === "requirements_engineer"`.
- New `SpecPage.tsx` with the layout above.
- Sidebar of stakeholder UI can stay as-is; SRE just doesn't visit it.
- Role-aware redirect after login: stakeholders go to `/`, SREs go to `/spec`.

## Scope options

1. **Read-only reviewer (1–2 days)** — SRE sees all sessions across
   users, can browse + export. No editing. Smallest change: new page
   with table view + role gate on list endpoints.
2. **Curator (3–5 days)** — adds inline editing, priority, status,
   acceptance criteria, merge/split actions. Most of the value, real
   work on schemas + UI table.
3. **Full collaboration (1–2 weeks)** — adds "needs clarification"
   loopback to stakeholder, comment threads on requirements,
   multi-stakeholder aggregation per project. Probably overkill for
   an FYP demo.

## Recommendation

**Option 2** is the sweet spot for an FYP — demonstrates that the
system supports the *full* RE workflow, not just elicitation. Option
1 is too thin for a defence; option 3 is too much for the timeline.

## Open questions before starting

- How is the SRE role assigned? (Manual promotion script? Signup
  toggle? Default first-account-becomes-admin?)
- Should SREs see ALL stakeholders' sessions or only ones explicitly
  shared / assigned to them?
- Does the stakeholder's UI need to show "needs clarification"
  feedback from the SRE, or is the loop manual/out-of-band for now?

## What is NOT in this plan

- Anything about the AI agent itself. The SRE role is purely a
  human-curation overlay on top of what the existing agent produces.
- Multi-tenant SaaS concerns. Still single-org for now.
